<details class="appendix-faq" id="kinematic-refinement">
<summary id="kinematic-question">How does HuMoTAR compare on kinematic retargeting?</summary>


We compare [GMR](https://arxiv.org/abs/2510.02252), [HOI-Retarget](https://arxiv.org/abs/2609.34674) and HuMoTAR on the same task set.

We follow [HOI-Retarget’s evaluation protocol (Appendix A)](https://arxiv.org/html/2609.34674v1#A1): **body pose deviation**, **link velocity direction error**, **contact-point gap** and **relative hand-orientation change** measure how well the robot preserves the human motion and object-relative contacts. We also report **body jerk** as a smoothness measure, the mean magnitude of the third time derivative of the palm, ankle, head and pelvis positions, estimated by finite differences. Lower values indicate smoother motion.

<details class="appendix-faq" id="semantic-evaluation">
<summary>How is semantic success evaluated?</summary>

The same Astra judging prompt compares the complete human demonstration and robot execution. A PASS means the main object interaction is substantially achieved. A FAIL means an essential action is missing or the object is lost before completion. An UNCERTAIN judgment is not counted as a pass. The prompt permits differences in robot posture, grasp and timing, as well as minor wobble or imperfect placement.

A separate opening-contact review checks for obvious initial hand–object penetration. Normal contact, small overlaps and ambiguous occlusion are not disqualifying. Suspected substantial intersections are reviewed with additional views; a collision-proxy measurement alone does not establish penetration. The reported semantic success rates use the original Astra judgments. The review-adjusted verdicts are retained separately and do not replace those judgments. It is not a collision audit of the entire motion.

Success rates use all 40 assigned tasks. The two-hour Codex condition has one incomplete execution, counted as unsuccessful. Tracking comparisons with this condition use the same 39 valid tasks for both methods. The other final tracking comparisons use all 40 tasks.

<details><summary>Original judging prompt</summary>

<pre class="judge-prompt">You receive two videos:
- Reference: the original human–object interaction.
- Candidate: the robot execution.

Does the candidate achieve the overall object interaction shown in
the reference?

Judge generously. Focus on what happens to the object across the
complete motion. Exact trajectory, timing, robot posture and grasp
need not match. Minor wobble and imperfect placement are acceptable.

PASS if the main interaction is substantially achieved.
FAIL if an essential part is missing or the object is lost before
the interaction is completed.

Check object rotation across multiple frames. Do not mistake an
intentional set-down for a drop. Do not require release or a stationary
ending unless the reference clearly makes it part of the interaction.

If the view does not provide enough evidence, return UNCERTAIN
instead of guessing.

Return:
- Verdict: PASS / FAIL / UNCERTAIN
- Reason: one or two sentences citing visible moments in the candidate.</pre>

<details class="appendix-faq" id="simulation-feedback">
<summary>What simulation feedback can the agents inspect?</summary>

After a rollout, agents can inspect rendered views and numerical measurements from the recorded execution:

- **Robot and object motion:** images of the execution and recorded poses and joint states.
- **Object tracking:** mean ADD, position error and orientation error relative to the target object trajectory.
- **Contact:** contact locations, normals and forces, including which robot and object surfaces touch.
- **Geometry and motion checks:** contact gaps, penetration, joint-limit margins and differences between reference and executed motion.

Agents can inspect these outputs with code and request further views or measurements. The observations they use depend on the trial; each iteration does not necessarily inspect every measurement.

</details>

<details class="appendix-faq" id="retargeting-tools">
<summary>Which tools and control interfaces can the agents use?</summary>

Agents can write their own analysis and control code. Two ensemble agents also receive a supplied retargeting-tools file, which they may use, modify or replace. These helpers expose the following measurements and interfaces; they do not prescribe a grasp or a refinement sequence.

**Table A2.** Interfaces available during refinement.

| Tool or interface | What it provides |
| --- | --- |
| Contact inspection | Contact locations, normals and forces from a saved execution, with close-up views. |
| Geometry checks | Contact gaps, surface alignment, penetration and joint-limit margins for a proposed pose. |
| Motion diagnostics | Link-position and orientation errors, and reference, command and execution joint traces. |
| Object-path evaluation | Mean ADD, position and orientation errors against the fixed target trajectory. |
| Whole-body control | A frozen tracking policy driven by a motion reference. |
| Custom joint control | Targets, gains and feedforward torques for the agent’s manipulation controller. |

</details>

<details class="appendix-faq" id="initial-reference-evaluation">
<summary>What does 0 minutes represent in the matched-time curves?</summary>

At 0 minutes, all three methods start from the initial kinematic reference executed with SONIC and the supplied finger targets. We evaluated these unchanged references for all 40 tasks using the original input bundles and the same object-tracking metric as the agent trials. These baseline evaluations were performed after the refinement experiments and are placed at 0 minutes to represent the reference available before refinement.

Each curve then retains the lowest object-tracking error among the initial reference and the completed agent trials. Every dataset mean includes the same tasks throughout. No later agent result is moved to 0 minutes. Semantic-success bars report the original final Astra judgments, separately from these object-tracking curves.

</details>

<details class="appendix-faq" id="results-longer-evidence">
<summary>What improves within the same two-hour run?</summary>

For each cutoff, we retrospectively select the lowest-ADD recorded execution that had finished by that time. It must have completed its reference and passed the recorded initial-object-pose and zero-velocity checks. The framework scores every trial against the same complete target trajectory. All three displayed errors come from the execution selected by ADD. Position and orientation errors can therefore increase even when ADD decreases.

Active time is reconstructed from the original call and each resume's stated remaining budget. Documented interruption gaps are excluded. Independently generated final verification replays are excluded from intermediate selection. This is a retrospective analysis of saved outputs, not a claim that an agent had computed every comparison score at that instant.

35 tasks have an eligible output by 30 minutes. On that fixed paired set, mean ADD falls from 30.17 to 10.65 cm and 33 tasks improve. Comparing the selected 30- and 120-minute manifests, reference-file hashes change on 31 tasks and initial-state hashes on 26. A changed hash establishes an artifact change, not its purpose or a semantic improvement. The other five tasks remain visible below without an invented early value.

Semantic comparisons reuse the existing Astra judgments for the separate 30-minute and 120-minute Codex experiments, with their existing opening-contact reviews. <summary>What is matched in the compute–time comparison?</summary>

The collaborative swarm receives four 30-minute worker budgets, totalling two agent-hours. The longer Codex condition receives one 120-minute budget, also totalling two agent-hours. Allocated agent-hours do not equate token counts, simulation counts, accelerator usage or native delegated-agent work.

The final semantic comparison includes all 40 tasks and counts the incomplete two-hour submission as unsuccessful. Tracking uses the same 39 valid final executions for both methods: 13.00 cm ADD for the collaborative swarm and 12.63 cm for two-hour Codex. The within-run table above uses different, retrospective selections and must not be substituted for these final submitted results.

Each condition has one recorded run per task. Differences between conditions combine workflow, budget and sampling effects. The within-run analysis tests whether later recorded outputs improve over earlier ones, but repeated runs would be needed to establish how reliably a workflow produces that improvement.
